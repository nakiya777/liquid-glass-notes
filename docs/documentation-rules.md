# 仕様書作成・更新ルール

- 文書種別: 開発運用規則
- ステータス: 現行
- 更新日: {{YYYY-MM-DD}}

## 1. 目的

仕様の正確性と追跡可能性を維持しつつ、AIと人が毎回読む文章量、修正時間、トークン消費を抑える。文書量を増やすことではなく、必要な判断を必要な場所から短時間で取得できることを優先する。

## 2. 基本原則

1. Markdownを唯一の正本とする。
2. 1つの事実を複数文書へ重複記載しない。
3. 現在の正解、判断理由、作業中メモを分離する。
4. 全文読込や全文上書きではなく、対象箇所の検索と差分更新を行う。
5. 仕様書を実装日記や作業報告書にしない。
6. コードの現状を理由なく仕様へ追認しない。仕様と実装が違う場合は差分として扱う。

## 3. 文書の役割

| 文書 | 記録する内容 | 記録しない内容 |
|---|---|---|
| `docs/INDEX.md` | 読むべき正本への案内、作業別マトリクス | 詳細仕様、変更履歴 |
| 領域別仕様書 | 現在の要求、振る舞い、制約、受入条件 | 長い議論、過去仕様 |
| ADR | 重要な設計判断、理由、代替案、影響 | 日常的な小変更 |
| Git履歴 | いつ、どの差分を変更したか | 仕様の説明本文 |
| Issue・作業メモ | 未確定案、調査、TODO、検証途中の情報 | 確定仕様 |
| `outputs/` | 提案・レビュー用成果物、過去スナップショット | 開発中に常時読む正本 |

## 4. 読み込むタイミングと範囲

### 作業開始時

1. `docs/INDEX.md`を読む。
2. 作業別マトリクスから対象仕様書を1個から2個選ぶ。
3. 重要判断が関係する場合だけADRを読む。
4. 対象コードとテストを確認する。

見出しや語句の位置だけ知りたい場合は、先に検索し、該当範囲だけ読む。

### 全体を読む条件

次のいずれかに該当する場合だけ、複数領域の仕様を横断確認する。

- 製品スコープや主要業務フローを変更する
- データモデル、API、計算結果が複数画面へ影響する
- リリース前の整合性レビューを行う
- 正本間の矛盾が発見された

初期設計スナップショットは履歴調査以外では読まない。

## 5. 仕様書を書き込む条件

次の場合は対象の正本を更新する。

- ユーザー要求または受入条件が追加、変更、削除された
- 画面の外部的な振る舞い、状態、権限が変わった
- APIまたはデータ契約が変わった
- 数量、見積、業務ルールなどの計算規則が変わった
- セキュリティ、保存、監査、外部送信の条件が変わった
- 複数実装へ影響する重要な設計判断が確定した
- 検証により、確定仕様の誤りや不足が判明した

次の場合は原則として更新しない。

- 外部挙動を変えないリファクタリング
- 変数名、関数名、内部ファイル配置の変更
- 既存仕様内のCSS微調整
- 一時的な実験、未採用案、調査ログ
- 単純な不具合修正で、元の仕様自体は正しかった場合

## 6. 書き込むタイミング

### 要求確定時

新しい外部仕様や受入条件が明確になったら、実装前に対象仕様へ最小限の変更を加える。要求が未確定なら正本へ書かず、作業メモやIssueで管理する。

### 設計判断時

将来の実装選択へ影響する判断が確定したらADRを作成する。ADR作成後、領域別仕様書には判断後の現在状態だけを反映する。

### 実装中

試行錯誤、仮説、調査結果を正本へ逐次追記しない。外部仕様が変わらない限り、コードとテストへ集中する。

### 実装・検証完了時

テストや画面確認後、仕様と実装の差分を確認する。外部仕様が変わった場合だけ正本を差分更新し、`docs/INDEX.md`の案内が古くなった場合だけ索引も更新する。

### リリース前

領域横断の整合性確認を一度行う。日々の作業ごとに全仕様書を読み直す代わりに、リリース境界でまとめて確認する。

## 7. 記述規則

- 1ファイル1責務を基本とする。
- 1ファイルが概ね250行を超え、異なる責務を含む場合は分割を検討する。
- 結論、外部挙動、受入条件を先に書く。
- 「予定」「検討中」「確定」を混在させず、未確定事項には明示的なラベルを付ける。
- 数値、単位、ステータス名、API名は曖昧語へ置き換えない。
- 同じ表や規則を複製せず、正本へリンクする。
- 変更履歴の羅列は本文へ追加せず、Git履歴を使用する。
- 文書全体を書き換えず、影響する段落、表、リンクだけを変更する。

## 8. 情報の優先順位

矛盾がある場合は、次の順で確認する。

1. マスターからの最新の明示指示
2. `docs/`配下の現行正本
3. 採用済みADR
4. テストで確認された実装状態
5. `outputs/`の過去資料

仕様と実装が矛盾した場合、勝手にどちらかへ合わせず、要求上の正解を確認してから修正する。

## 9. 完了条件

文書を作成、更新した作業は、次を満たして完了とする。

- 対象文書が正しいディレクトリにある
- `docs/INDEX.md`から必要な正本へ到達できる
- 同じ仕様が別ファイルへ重複していない
- 相対リンクが壊れていない
- 外部仕様と実装の差分が説明できる
- ファイル索引更新コマンドを実行している（プロジェクトに存在する場合）
- 関係するテスト、型検査、ビルドを実行している

## 10. AIへの標準指示

```text
最初に docs/INDEX.md を読み、作業対象に必要な仕様書だけを取得すること。
全仕様書や初期スナップショットを一括で読み込まないこと。
外部仕様が変わらない修正では仕様書を更新しないこと。
仕様変更は対象箇所だけ差分更新し、設計理由が必要な場合はADRへ記録すること。
実装と検証が完了してから、仕様と実装の整合性を最終確認すること。
```
